# CIP-0002: Themed grouping for available student projects

## Status

- [x] Proposed - Initial idea documented
- [x] Accepted - Approved, ready to start work
- [x] In Progress - Actively being implemented
- [x] Implemented - Work complete, awaiting verification
- [ ] Closed - Verified and complete

## Summary

Allow entries in `_availableprojects` to act as **themes** that group
concrete student projects (and nested themes). Top-level project lists show
themes and unthemed projects only; children appear under their theme page.
Person/supervisor lists follow the parent-wins rule described below.

## Motivation

Related Part II / Part III / MPhil briefs often share a research framing,
prerequisites, and supervisors. Listing every brief at the top level makes the
available-projects pages hard to scan. Editors need a way to publish a theme
summary once and attach individual briefs underneath, without maintaining a
bidirectional child list.

## Detailed Description

### Data model

Themes and projects live in the same `availableprojects` collection.

| Concern | Rule |
| --- | --- |
| Distinguishing a theme | `layout: available-project-theme` |
| Distinguishing a project | `layout: project-to-supervise` (existing default) |
| Parent link | Optional frontmatter `theme: <slug>` on the **child** |
| Child lists on themes | **None** — children are discovered by `theme == this.slug` |
| Cardinality (v1) | At most one parent theme per entry |

Nested themes are allowed: a theme may itself set `theme: <parent-slug>`.
In every list that applies the hierarchy rules, a nested theme behaves like a
sub-project (hidden when an ancestor is shown). On its own page it still acts
as a theme (lists its children).

### Listing rules

1. **Top-level lists** (`/internal/projects/`, completed list, and any similar
   aggregate): show an entry only if `theme` is blank. Themes and standalone
   projects appear; children do not.
2. **Theme page**: list all non-`Hidden` entries with `theme: <this-slug>`
   (projects or nested themes), sorted by title.
3. **Person / supervisor lists**: for each entry the person supervises, show it
   only if they are **not** also a supervisor of any ancestor theme. Equivalently:
   - on a theme → show the theme; suppress descendants
   - on a child only → show that child

Walking ancestors follows `theme` pointers up to a fixed depth (cycle guard).

### Theme page content

Themes reuse the editorial fields that matter for framing:

- title, status, categories, overview, prerequisites, supervisors
- optional related group `projects`
- optional body

They do **not** require the student FAQ fields (`student_learn`,
`project_objective`, `project_bigger_picture`), though editors may leave them
empty if the CMS shows them for the shared collection.

### Decap CMS

Same `availableprojects` collection:

- `layout` becomes an editor-visible select:
  `project-to-supervise` | `available-project-theme`
- new optional `theme` relation → `availableprojects`, filtered to entries
  with theme layout where the CMS supports that filter

### Theme gem / site split

| Location | Change |
| --- | --- |
| `mlatcl/jekyll-theme` | New layout `available-project-theme`; shared visibility include; person/supervisor list filtering; optional parent link on project pages |
| `mlatcl/mlatcl.github.io` | Decap schema; top-level list pages use visibility include; CIP |

## Implementation Plan

1. Document design in this CIP (done).
2. Add theme layout and `availableproject-list-visible` include in the theme gem.
3. Filter supervisor-projects (and any other theme-owned lists) with person mode.
4. Update Decap `availableprojects` fields (`layout` select, `theme` relation).
5. Update site list pages (`available-projects.html`, `completed_projects.html`).
6. Optionally link from a child project page up to its parent theme.
7. Smoke-check Liquid logic with a sample theme + nested child (content can
   follow in a later edit).

## Backward Compatibility

- Existing briefs without `theme` and with `layout: project-to-supervise`
  behave exactly as today.
- No content migration required until editors create themes and set `theme:`
  on children.
- Remote theme must be updated (or pinned) before theme layouts resolve on
  GitHub Pages.

## Testing Strategy

- Create a draft theme and two children; confirm top-level list shows the theme
  only.
- Confirm theme page lists both children.
- Assign a person to the theme only → person list shows theme only.
- Assign a person to one child only → person list shows that child.
- Assign a person to both → person list shows theme only.
- Nested theme under a parent theme → top-level shows parent only; nested theme
  appears on parent page; children of nested theme appear on nested theme page.
